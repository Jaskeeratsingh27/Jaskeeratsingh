# V1.4 deployment runbook

## What V1.4 runs

The V1.4 process drains the durable V1.3 outbox and performs authenticated Jira side
effects. GitHub App auth is implemented and tested for future GitHub-side outbox
operations.

## Required durable storage

Mount a persistent volume at /data or override:
- CONTROL_PLANE_DB_PATH
- CONTROL_PLANE_ROTATING_SECRETS_PATH

The SQLite database and encrypted rotating-token file must survive container restarts.

## Jira OAuth bootstrap

Create one Atlassian OAuth 2.0 (3LO) integration and obtain offline access with the
least privileges required. Configure JIRA_CLOUD_ID, client ID, client secret and the
initial refresh token as platform secrets.

Atlassian rotates refresh tokens. The worker writes the replacement token to the
encrypted rotating-secret file before accepting the new access token.

## Secret encryption

CONTROL_PLANE_SECRET_KEY is a Fernet key and must be supplied by the hosting
platform's secret manager. The key and OAuth secrets must never be committed.

## GitHub App

For unattended GitHub-side operations, create/install a GitHub App with the narrowest
repository permissions needed. Supply app ID, installation ID and private key through
the deployment secret manager. Installation tokens are generated dynamically.

## Run

Build:

    docker build -f projects/github-jira-manager/Dockerfile.worker -t gjm-worker .

One drain for validation:

    docker run --rm ... gjm-worker python /app/src/worker_main.py --once

Long-running:

    docker run ... gjm-worker

## Current V1.4 live boundary

CI proves authentication protocol handling and provider calls against isolated fake
GitHub/Jira APIs. A real hosted test cannot be completed until the GitHub App and Jira
OAuth integration credentials are created by the account owner and injected into the
hosting platform's secret manager.
