# V1 Architecture

## Design objective

Create the smallest auditable architecture that can later manage Jira and GitHub safely from natural-language instructions without making ChatGPT, Jira, or Hermes a hard dependency.

## Logical architecture

```
Human
  |
  v
Orchestrator
  |--------------------|----------------------|
  v                    v                      v
Project Manager   Software Engineer      QA / Validation
  |                    |                      |
  v                    v                      v
Jira adapter       GitHub adapter        CI/test adapter
  \____________________|______________________/
                       |
                       v
                Policy + job state
```

## Source-of-truth boundaries

| Domain | Canonical system |
|---|---|
| Code | GitHub |
| Agent specifications | GitHub |
| Architecture/docs | GitHub |
| Released version | GitHub |
| Backlog/issues | Jira |
| Project status | Jira |
| Dependencies/milestones | Jira |
| Runtime execution state | Control plane |
| CI/test evidence | GitHub Actions / test runner |

No component may silently overwrite another system's authority.

## Agent responsibility boundaries

### Orchestrator
May plan, route, inspect status, request approvals, and reconcile results.
Must not directly mutate code or self-certify QA.

### Project Manager
May create/update Jira planning objects through approved tools.
Must not write code or mark implementation verified without QA evidence.

### Software Engineer
May read repositories, create branches, modify branch content, commit, and open PRs.
Must not push to protected branches or merge its own PR.

### QA / Validation
May inspect diffs, acceptance criteria, CI, tests, and policy state.
Must not implement the feature it is certifying in the same execution role.

## Approval tiers

- **L0 Read-only** — automatic.
- **L1 Safe write** — automatic within bounded scope.
- **L2 Review required** — requires human approval before execution.
- **L3 Explicit/destructive** — always requires explicit human approval.

## Initial workflow

```
IDEA
 -> DISCOVERY
 -> PLANNED
 -> READY
 -> IN_PROGRESS
 -> CODE_COMPLETE
 -> VALIDATION
 -> REVIEW
 -> READY_TO_MERGE
 -> DONE
```

Exceptional states: BLOCKED, INPUT_REQUIRED, FAILED, CANCELED.

A work item cannot transition to DONE unless it has passed VALIDATION and REVIEW.

## Reliability requirements

1. Every mutating operation must have an operation ID for idempotency.
2. Every execution must have a run ID for correlation.
3. Every L2/L3 action must record approval.
4. Retry logic must not duplicate Jira issues, branches, PRs, or releases.
5. Agent output is advisory unless converted into a permitted tool action.
6. Tool permissions are narrower than agent prompts.

## V1 implementation strategy

V1 uses deterministic mock adapters. This is intentional: orchestration and policy must be testable without external credentials or API variance.

V1.1 will replace mocks with a read-only GitHub/Jira integration test layer.
V1.2 will add bounded writes.
