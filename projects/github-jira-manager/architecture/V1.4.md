# V1.4 Architecture — authenticated side-effect worker

## Goal

Turn the durable V1.3 outbox into real provider API actions without embedding interactive ChatGPT credentials.

## Flow

Webhook receiver → durable event → reconciliation → outbox → worker → provider auth → Jira/GitHub API → outbox acknowledgement.

## Auth model

### GitHub
Use a GitHub App installation. The worker signs an app JWT with RS256, exchanges it for an installation token, caches it only until shortly before expiry, and requests a new one when needed.

### Jira
Use OAuth 2.0 (3LO) with offline access. Access tokens are refreshed from a rotating refresh token. The replacement refresh token must be durably saved before the worker accepts the newly issued access token.

## Retry model

- Network errors, 429 and 5xx: retry with bounded exponential backoff.
- Unsupported operations or impossible workflow transitions: dead-letter.
- 401: invalidate cached access token and re-authenticate once inside the provider client; persistent failure returns to worker retry policy.

## Delivery guarantee

The worker is at-least-once at the network boundary. The durable operation ID prevents logical duplication inside the control plane, but no claim of network-level exactly-once execution is made.

## Secret model

Static client secrets/private keys come from the hosting secret manager. Rotating Jira refresh-token state must be writable to secure durable storage. The reference implementation provides an encrypted persistent file for single-node deployment and an interface boundary for a managed secret store.

## Live deployment gate

The code can be merged without real credentials. Production deployment requires user-created GitHub App/Jira OAuth credentials and a host with persistent storage plus secret injection.
